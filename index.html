03 · Parte 2

Modelos de Regresión

Implementación de tres tipos de regresión para predecir variables continuas, con análisis de desempeño mediante R² y MSE.

📈
Regresión Lineal Simple

Modela la relación entre una variable predictora X y una variable de respuesta Y mediante una línea recta. Ideal para relaciones lineales directas.

ŷ = β₀ + β₁·x
β₁ = Σ(xᵢ-x̄)(yᵢ-ȳ) / Σ(xᵢ-x̄)²
R² Score0.87
MSE12.4
Datos de entrenamiento vs línea de regresión
📊
Regresión Lineal Múltiple

Extiende la regresión simple a múltiples variables predictoras. Captura relaciones complejas entre varias características y la variable objetivo.

ŷ = β₀ + β₁x₁ + β₂x₂ + ... + βₙxₙ
β = (XᵀX)⁻¹ · Xᵀy
R² Score0.92
MSE7.8
Valores reales vs predicciones del modelo
📉
Regresión Polinómica

Captura relaciones no lineales al incluir potencias de las variables predictoras. Mayor flexibilidad con riesgo de sobreajuste si el grado es alto.

ŷ = β₀ + β₁x + β₂x² + β₃x³
Grado óptimo: d=3 (validación cruzada)
R² Score0.96
MSE4.2
Curva polinómica de grado 3 ajustada

05 · Flujo

Git Workflow

Proceso completo desde el commit hasta el merge en develop, siguiendo el flujo GitFlow adaptado para trabajo en equipo.

COMMIT

git add . && git commit

Se registran los cambios con mensajes semánticos: feat: add linear regression model

PUSH

git push origin feat/regresion

Se sube la rama feature al repositorio remoto en GitHub para revisión del equipo.

PULL REQUEST

PR: feat/regresion → develop

Solicitud de fusión con descripción de cambios, capturas de métricas y aprobación de al menos 1 revisor.

MERGE

Merge a develop → main

Integración de cambios revisados. Merge squash a main para mantener historial limpio y etiquetado con versión.

📋 Commits semánticos
feat: add polynomial regression
fix: handle missing values in data
docs: update README with results
test: add unit tests for metrics
refactor: extract preprocessing utils
🔃 Comandos Git utilizados
$ git checkout -b feat/regresion develop
$ git add models/linear_regression.py
$ git commit -m "feat: add linear regression"
$ git push origin feat/regresion
$ git checkout develop && git merge feat/regresion
06 · Resolución

Resolución de Conflictos

Cuando dos ramas modifican las mismas líneas, Git genera marcadores de conflicto que deben resolverse manualmente antes del merge.

⚠️
¿Cuándo ocurre?
  • 🔸 Dos ramas modifican la misma línea
  • 🔸 Un archivo fue eliminado en una rama y modificado en otra
  • 🔸 Cambios en el mismo bloque de código simultáneamente
🛠️
Pasos para resolver
  • 1️⃣ git status — identificar archivos en conflicto
  • 2️⃣ Editar el archivo y elegir los cambios correctos
  • 3️⃣ git add <file> — marcar como resuelto
  • 4️⃣ git commit — finalizar el merge
📄 Ejemplo de conflicto en models/config.py
<<<<<<< HEAD (develop)
LEARNING_RATE = 0.01
MAX_ITER = 1000
=======
LEARNING_RATE = 0.001
MAX_ITER = 5000
>>>>>>> feat/clasificacion

# ✅ Resolución: mantener valores de feat/clasificacion (mayor convergencia)
LEARNING_RATE = 0.001
MAX_ITER = 5000

08 · Cierre

Conclusiones

🧠
Machine Learning

La evaluación demostró que la complejidad del modelo no siempre es la mejor estrategia. La regresión polinómica de grado 3 alcanzó el mejor R² (0.96) para datos con tendencia no lineal, mientras que la regresión logística obtuvo un 95.3% de accuracy en clasificación binaria. El preprocesamiento cuidadoso de datos (manejo de nulos, escalado) fue determinante para la calidad de las predicciones. Se comprobó la importancia de validar con datos no vistos para detectar sobreajuste.

🔀
Git & Colaboración

El flujo de trabajo con GitFlow permitió desarrollar múltiples funcionalidades en paralelo sin interferencias. Las ramas feature aislaron el desarrollo de cada modelo, y los pull requests facilitaron la revisión de código antes de integrar a develop. La resolución de conflictos, aunque desafiante, fortaleció las habilidades del equipo en el uso avanzado de Git. El uso de commits semánticos mejoró la trazabilidad del historial del proyecto.
